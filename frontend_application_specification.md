# SG Investing Frontend Application Specification

## 1. Purpose

Build a static, Singapore-investor-focused web application that presents the
results of the `sg_investing` analytics engine. The frontend helps a user
understand historical investment outcomes in a security's native currency and
in SGD, including the effect of dividends, withholding tax, and FX.

The frontend is a presentation and input layer. It must never reproduce the
financial calculations in browser code. All figures are supplied by backend
generated JSON artifacts or a future thin read-only API.

> **Architecture decision (2026-08-31, ADR 0001).** For the fully static
> GitHub Pages deployment, the "no browser calculation" rule above is
> superseded by a portable calculation engine: a browser-native ES-module
> JavaScript port of the Python engine (vendored decimal arithmetic, executed
> in Web Workers, no build step), gated by comprehensive golden parity tests
> against the Python engine. Until that port proves parity (Todo sprints 2–3),
> the Python engine and its artifacts remain the only authoritative source of
> figures. See `docs/adr/0001-calculation-architecture.md`.

This document translates the backend product design document and the currently
implemented Python package into a frontend delivery specification. It does not
change the backend's financial methodology.

## 2. Product principles

- **SGD-first, native-currency-aware.** Default to SGD for a Singapore-based
  investor, while allowing a clear switch to the security's native currency.
- **Explain material assumptions.** A user must be able to see how a result was
  calculated and any warnings affecting it.
- **Observed data vs. investor modelling.** Price history is observed; dividend
  withholding and reinvestment are explicit model assumptions.
- **No hidden costs or deductions.** Do not imply brokerage, FX conversion
  costs, slippage, sale costs, or an extra TER deduction are included.
- **Static-site compatible.** The target is GitHub Pages or another static host.
  It should work from pre-generated, versioned JSON rather than requiring a
  continuously running application server.

## 3. Scope

### In scope for the first frontend release

1. Security discovery from the configured universe.
2. Single-investment historical analysis.
3. Native-currency / SGD presentation switcher.
4. Scenario presets and dividend/tax/reinvestment controls.
5. Data-quality warnings, methodology, and limitations.
6. DCA analysis when DCA result artifacts are supplied.
7. Read-only portfolio results when portfolio result artifacts are supplied.

### Explicitly out of scope

- Order execution, brokerage connectivity, account aggregation, and trading.
- Browser-side reimplementation of return, XIRR, tax, or FX calculations.
- Authentication, persistence of sensitive financial data, and cloud database
  infrastructure in V1.
- Intraday quotes or charts.
- User-selectable ETF expense-ratio deductions.
- Fees, FX conversion charges, and slippage modelling until the backend supports
  them explicitly.

## 4. User and primary questions

The primary user is an individual Singapore investor evaluating global and SGX
securities. The application should answer:

- “If I invested S$10,000 in this security over this period, what would it be
  worth?”
- “How much of the outcome is local-currency price movement versus USD/SGD FX?”
- “What changes if I include dividends, withholding tax, and reinvestment?”
- “What would fixed regular contributions have returned?”
- “What are my recorded holdings worth today?”

The app is educational and analytical. It must not provide personalised
investment advice or make forecasts.

## 5. Information architecture

| Route / view | Purpose | Primary backend result |
| --- | --- | --- |
| Home | Explain the tool, data coverage, and start an analysis. | Universe summary and freshness metadata |
| Explore | Search/filter the security catalog. | Catalog security and membership records |
| Security analysis | Configure and view one historical investment scenario. | `AnalysisResult` |
| Compare | Compare saved analysis result artifacts with identical inputs. | Multiple `AnalysisResult` artifacts; backend comparison endpoint/artifact later |
| DCA | Configure and display recurring-investment results. | `DcaResult` |
| Portfolio | View imported/processed portfolio result artifacts. | `PortfolioResult` |
| Methodology | Explain return, FX, dividend, tax, and data conventions. | Versioned static content and result methodology |

For the first release, the Home and Security analysis views are the essential
path. Compare, DCA, and Portfolio can be introduced as separate releases when
their result artifacts are generated by the backend build pipeline.

## 6. Navigation and global UI

### Header

- Product name and Home link.
- Explore, Analyse, DCA, Portfolio, and Methodology navigation.
- A visible “Data as of” timestamp based on the published artifact manifest.
- A short “Historical analysis, not financial advice” disclosure.

### Shared controls

- Native currency / SGD segmented control, labelled with the security currency:
  `USD | SGD`, `EUR | SGD`, or `SGD` only for an SGD security.
- Consistent date input with ISO date validation and a readable local display.
- Currency and percentage formatting that preserves sufficient precision in
  tooltips while rounding only for presentation.
- Empty, loading, no-data, and failed-artifact states.
- Accessible keyboard and screen-reader labels for charts, controls, warnings,
  and formatted financial values.

### Responsive behaviour

- Desktop: analysis input panel beside headline results; tables fully visible.
- Tablet: input panel above results; result cards in two columns.
- Mobile: one-column cards; tables use a labelled stacked layout or controlled
  horizontal scrolling. The currency switcher remains visible near results.

## 7. Security discovery

### Search and filter

Allow search by ticker, provider-specific ticker, name, ISIN, market, or
exchange. Provide filters for:

- Asset type: equity, ETF, index, REIT, trust, other.
- Market/exchange and native currency.
- Universe membership, including configured major ETFs, current S&P 500,
  Nasdaq-100, Russell 2000, SGX listings, and future universe snapshots.
- Distribution policy: accumulating, distributing, unknown.
- Active/inactive status.

### Security card and detail metadata

Show ticker, name, exchange, native currency, asset type, domicile, ISIN when
available, distribution policy, and expense ratio when available. State that
expense ratio is metadata and is not deducted again from observed performance.

Provider ticker and exchange must be displayed together where ambiguity exists;
the UI must not treat ticker alone as a global identifier. For example, the
configured VALL listing should display its provider ticker and SIX exchange.

## 8. Single-investment analysis

### Input panel

Required inputs:

- Security.
- Initial investment in SGD; the initial release accepts SGD only because the
  current `analyze_security` contract accepts `initial_sgd`.
- Start date and end date.

Scenario controls map directly to `AnalysisScenario`:

| UI control | Result setting | Default |
| --- | --- | --- |
| Include dividends | `dividends_enabled` | On |
| Apply dividend withholding tax | `withholding_tax_enabled` | On |
| Reinvest net dividends | `reinvest_dividends` | On |
| Purchase-date convention | `purchase_date_rule` | Next trading day |
| Valuation-date convention | `valuation_date_rule` | Previous trading day |

Date-convention controls may initially be presented as read-only defaults if no
other backend-supported values are offered. Do not expose an unsupported choice.

### Scenario presets

Implement these visible presets, each of which updates the three scenario
controls above:

| Preset | Dividends | Withholding | Reinvestment |
| --- | --- | --- | --- |
| Price only | Off | N/A | N/A |
| Gross total return | On | Off | On |
| Singapore investor return | On | On | On |
| Singapore investor cash-dividend return | On | On | Off |

The controls remain visible after a preset is selected so the user can see and
modify its assumptions. There must be no “deduct TER” control.

### Result layout

Place the following summary in the first viewport after a calculation:

1. Final value.
2. Total return.
3. CAGR.
4. Initial investment and resolved start/end dates.
5. A native currency / SGD switcher.

Below this, use sections or tabs for Price & FX, Dividends, Holdings, and
Methodology & data quality.

#### Currency-mode mapping for `AnalysisResult`

| Display item | Native-currency mode | SGD mode |
| --- | --- | --- |
| Initial investment | `initial_investment_foreign_currency` | `initial_investment_sgd` |
| Price return | `price_return.foreign_currency` | `price_return.sgd` |
| Final security value | `investment.final_security_value_foreign_currency` | Show its SGD equivalent only if supplied; otherwise show it as supporting native detail |
| Final total value | `investment.final_value_foreign_currency` | `investment.final_value_sgd` |
| Total return | `returns.total_return_foreign_currency` | `returns.total_return` |
| CAGR | `returns.cagr_foreign_currency` | `returns.cagr` |
| Gross dividends | `dividends.gross_foreign_currency` | `dividends.gross_sgd_at_payment` |
| Withholding tax | `dividends.withholding_tax_foreign_currency` | `dividends.withholding_tax_sgd_at_payment` |
| Net dividends | `dividends.net_foreign_currency` | `dividends.net_sgd_at_payment` |
| Cash dividends | `dividends.cash_foreign_currency` | Do not derive a value in browser; present native detail unless a backend SGD cash field is added |

`foreign_currency` means the security's native currency. For a US asset, label
it as USD throughout the interface; never show “foreign currency” to an end
user.

The unqualified `returns.total_return` and `returns.cagr` are SGD-based legacy
fields. The frontend must use their `*_foreign_currency` counterparts for the
native mode, rather than deriving a return itself.

### Price, FX, and value visualisation

The backend stores daily unadjusted OHLCV data, but `AnalysisResult` does not
currently include a time series. A chart requires a separately generated,
versioned series artifact. Until it exists, show summary cards only.

When a chart artifact is available, provide:

- Local-currency close chart.
- SGD-converted value/return chart for the selected scenario.
- Optional FX-rate overlay or a separate USD/SGD chart.
- A chart legend that states daily-close data, local-exchange trading dates, and
  whether values are native currency or SGD.

Do not synthesise a historical portfolio-value line from only the final result
in browser code.

### Dividends section

Show gross dividends, withholding tax, net dividends, and whether dividends
were reinvested or retained as cash. When the SGD view is selected, label the
SGD dividend figures as “translated at payment-date FX”; this differs from the
valuation-date conversion used for final value and SGD return.

For accumulating ETFs, explain that no investor cash dividend is invented and
that observed price/NAV performance is used instead.

## 9. DCA analysis

### Inputs

- Security, start date, end date.
- Contribution in SGD.
- Frequency: monthly, quarterly, yearly.
- The same dividend/tax/reinvestment scenario controls as single-investment
  analysis.

The UI must state that each contribution occurs on the first available trading
day in the selected period.

### Results

Show contribution dates, shares, total contributed, final value, gain/loss, and
money-weighted return (XIRR). The native/SGD display switch maps as follows:

| Native mode | SGD mode |
| --- | --- |
| `total_contributed_foreign_currency` | `total_contributed_sgd` |
| `final_value_foreign_currency` | `final_value_sgd` |
| `gain_loss_foreign_currency` | `gain_loss_sgd` |
| `xirr_foreign_currency` | `xirr` |

Label XIRR as a money-weighted return. Do not label it CAGR.

## 10. Portfolio view

The current portfolio engine reconstructs holdings from a transaction ledger
using weighted-average cost basis. The frontend must use a generated
`PortfolioResult` rather than calculate holdings itself.

Display:

- As-of date and total market value in SGD.
- Holdings table: ticker, quantity, weighted average cost, native market value,
  SGD market value, realised P/L, and unrealised P/L.
- Cash by currency and realised P/L by currency.
- An explicit note: “Weighted-average cost is a reporting convention, not a
  Singapore capital-gains tax calculation.”

The current result does not provide portfolio-level return, XIRR, allocation,
or time series. Do not show these as calculated facts until the backend provides
them. A future portfolio currency switcher requires an explicit portfolio-level
native reporting currency field; individual holdings already carry native and
SGD values.

## 11. Comparison view

The product design specifies comparable scenarios and securities, but the
current high-level engine only exposes single-security analysis. Implement this
view after the publishing layer can supply multiple compatible `AnalysisResult`
artifacts or a dedicated backend comparison contract.

Requirements when enabled:

- Apply the same initial SGD amount and date range across compared results.
- Display each scenario's inputs beside outputs.
- Keep native and SGD comparisons separate; never compare a USD percentage card
  to an SGD percentage card without a clear mode label.
- Flag inconsistent data snapshots or methodology versions.

## 12. Data artifacts and integration contract

### Required artifact categories

The static build/publishing process should produce:

```text
public/data/
  catalog.json
  data-status.json
  analyses/<request-key>.json
  dca/<request-key>.json
  portfolios/<portfolio-key>.json
  comparisons/<comparison-key>.json
  series/<security-id>/<range>.json        # adapter response; publishable JSON shape
```

`request-key` must be a deterministic hash or canonical serialisation of the
security ID, dates, initial SGD amount, scenario, methodology version, and data
snapshot identifier. A user-sharable URL may contain the human-readable inputs,
but browser code must request a matching precomputed artifact rather than run a
financial calculation.

### Current Python contracts

- `SGInvestingEngine.analyze(...)` returns `AnalysisResult` and is the current
  high-level application-facing entry point.
- `dca_analysis(...)` returns `DcaResult`; `scripts/frontend_server.py` exposes
  the same shape at `/api/dca` for the local/read-only application adapter.
- `analyze_portfolio(...)` returns `PortfolioResult`; the adapter exposes it at
  `/api/portfolio` using a POST ledger payload.
- `UniverseCatalog` supplies security and universe metadata.

All API values are Pydantic-serializable JSON. Decimal values may be serialised
as strings; the frontend must parse them with a decimal-safe formatter and must
not use binary floating-point arithmetic for financial calculations.

### Artifact metadata

Every published result should include, either inside the result or in an
envelope:

```json
{
  "generated_at": "2026-08-30T00:00:00Z",
  "data_snapshot_id": "...",
  "catalog_version": "...",
  "methodology_version": "1.0",
  "result": {}
}
```

The current analysis result exposes its methodology version. The publishing
adapter should add snapshot/provenance fields because price manifests already
record pipeline version, source, retrieval time, and coverage.

### Integration gaps resolved for the current frontend

1. A thin read-only compute service is implemented in
   `scripts/frontend_server.py`; the browser requests JSON and never executes
   financial calculations. The checked-in QQQ artifact remains the static
   fallback for offline/demo use.
2. DCA and portfolio adapter methods are implemented and return the canonical
   `DcaResult`/`PortfolioResult` fields in the standard result envelope.
3. `/api/series` implements the explicit daily-series shape consumed by the
   chart, with native close, SGD close, FX rate, date, and provenance fields.
4. `frontend/data/catalog.json` is generated from `current_catalog.json`, and
   `frontend/data/data-status.json` records coverage/freshness. The UI also
   supports ticker, name, ISIN, market, exchange, asset, universe, currency,
   distribution and active-status filters.
5. `/api/compare` applies one shared request lens to 2–6 catalog tickers and
   returns compatible envelopes for side-by-side display.

The deployment can use the adapter directly or replace each response with a
pre-generated artifact having the same envelope. A static host alone still
needs a publishing job for arbitrary user-selected requests.

### GitHub Pages release path

The checked-in `.github/workflows/pages.yml` publishes `frontend/` as a static
GitHub Pages artifact on pushes to `main` and on manual dispatch. The frontend
has no bundler or server-side runtime requirement. Empty `sg-invest-api-base`
metadata keeps the site in static replay mode; setting that metadata to an
HTTPS adapter origin enables dynamic requests without moving financial
calculation logic into the browser. Static mode remains intentionally limited to
the checked-in artifacts and must not imply that every catalog security has a
published result.

## 13. Methodology and warnings

### Required methodology disclosure

Every result page must make these facts available without leaving the page:

- Prices are daily local-exchange closes.
- Purchase resolves to the next available trading day; valuation resolves to the
  prior available trading day, unless the backend result states otherwise.
- FX convention is one unit of native currency equals X SGD.
- Investor-level dividend withholding is configurable and distinct from fund
  tax drag.
- Reinvestment uses the pay-date close convention, permits fractional shares,
  and may use a 30-day ex-date fallback if pay date is absent.
- TER is metadata and is not deducted again from observed ETF performance.
- Results are mark-to-market; V1 excludes transaction, conversion, and slippage
  costs and does not assume a sale at the valuation date.

### Warning treatment

Map `data_quality.status` to a visible badge:

| Status | UI treatment |
| --- | --- |
| `OK` | Quiet success label or no badge. |
| `WARNING` | Amber badge plus expandable warning list. |
| `INCOMPLETE` | Prominent warning; prevent statements that imply full coverage. |
| `FAILED` | Error state with retry/back navigation; do not show stale figures as current. |

Warnings must remain attached to copied/exported results. Examples include an
estimated dividend pay date, an unavailable tax rule treated as 0%, and dividend
cash falling after the valuation date.

## 14. Accessibility, formatting, and trust

- Meet WCAG 2.2 AA for contrast, focus visibility, form labels, error messages,
  and non-colour indicators of gains/losses.
- Use `S$` or `SGD` consistently; label native currencies with ISO codes such as
  USD, EUR, or HKD.
- Pair positive/negative colour with `+`/`−` signs and clear text.
- State whether a percentage is price return, total return, CAGR, or XIRR.
- Do not round data used in displayed relationships before formatting; use a
  documented display precision and disclose exact values in accessible labels or
  tooltips when helpful.
- Provide a “Copy analysis link” and “Download result JSON” action only when the
  link/artifact preserves inputs, methodology version, and data-snapshot ID.

## 17. Iterative implementation roadmap

This roadmap is intended to guide an implementation agent through small,
testable increments. Each iteration should end with a usable vertical slice,
not merely a collection of UI components. Do not start an iteration that needs
backend data artifacts until its dependency is available or an approved static
fixture represents the contract.

### Working cadence

- Treat each iteration below as a short sprint (normally one week or less).
- At sprint start, confirm the relevant JSON contract and acceptance checks.
- During implementation, use representative static fixtures only for UI
  development; do not embed mock calculation logic into production code.
- At sprint end, run automated checks, manually verify desktop and mobile
  layouts, and record any contract gaps as backlog items.
- Preserve the backend's methodology labels and warnings verbatim where
  possible. Frontend copy may clarify them but must not change their meaning.

### Mandatory Chrome design and UX QA gate

**This is a required execution rule for every agent implementing the frontend.**
The agent **MUST use Chrome** to inspect the rendered application after every
sprint that changes user-facing frontend behaviour and before claiming that a
frontend task is complete. Code review, unit tests, snapshots, and static
inspection are useful but do not replace this Chrome check.

If Chrome control is unavailable, the agent must report it as a delivery
blocker, direct the user to enable the Chrome browser extension in **Settings →
Computer use**, and wait for the required visual QA to be completed. The agent
must not substitute another browser or mark the frontend work complete without
recording this limitation.

For each Chrome QA pass, the agent must:

1. Open the locally running or deployed frontend in Chrome and inspect the
   actual rendered page, not source code alone.
2. Test the changed primary flow end to end. For example: find QQQ, configure
   an analysis, view the result, switch `USD | SGD`, open methodology, and
   inspect an injected warning/error state where relevant.
3. Check at least three responsive widths: desktop (1440px), tablet (1024px),
   and mobile (390px). Check that cards, forms, tables, charts, and the currency
   switcher remain usable without clipped controls or unintended horizontal
   scrolling.
4. Test keyboard navigation: logical focus order, visible focus state, usable
   segmented controls, form validation announcements, modal/dialog escape
   behaviour when present, and no keyboard trap.
5. Inspect each financial display for currency labels, sign/percentage labels,
   date labels, warning visibility, and methodology context. The agent must
   confirm that native mode names the actual currency (for example USD), while
   SGD mode names SGD/S$.
6. Verify the applicable design and user-experience principles listed below.
7. Capture or retain Chrome screenshots for the changed desktop and mobile
   states when the task permits artifacts. Record the URL/build, viewports,
   flows tested, defects found, and fixes made in the sprint review.
8. Fix all critical issues before closing the sprint. A remaining non-critical
   issue must be logged explicitly with user impact and a follow-up owner.

#### Design principles the Chrome check must enforce

- **One clear next action.** Each view has one visually dominant action; for the
  core path it is selecting a security or running the analysis. Secondary
  controls never compete with it.
- **Immediate financial context.** Every financial figure identifies its
  currency and metric type (price return, total return, CAGR, or XIRR). Users
  must not infer this from placement or colour alone.
- **Mode clarity.** The active USD/native or SGD mode is visually obvious and
  changing it updates every supported figure in the same results region. Mixed
  currency units must never appear as if directly comparable.
- **Progressive disclosure.** Headline value, total return, and CAGR appear
  first. Dividend detail, FX detail, methodology, provenance, and limitations
  are available nearby without obscuring the primary answer.
- **Trust before polish.** Warnings, data freshness, resolved dates, and
  methodology assumptions are visible when relevant. A visually attractive
  result must not hide an incomplete or estimated input.
- **Plain-language guidance.** Explain investor concepts in concise language;
  preserve technically precise backend terminology in the methodology panel.
  Do not make a user decipher implementation-field names such as
  `foreign_currency`.
- **Accessible by default.** Text meets contrast requirements; status is not
  colour-only; touch targets are comfortably sized; text remains readable at
  200% browser zoom; and charts/tables have equivalent text alternatives.
- **Calm, focused density.** Avoid dashboard clutter. Prefer grouped cards,
  intentional spacing, short labels, and expandable detail over showing every
  available data point at once.
- **Honest empty and failure states.** Loading, missing-data, malformed-artifact,
  and stale-data states explain what happened and offer a safe next action.
  They never display fabricated values or silently fall back to calculations in
  the browser.

#### Chrome QA definition of done

A frontend sprint is not complete until its sprint review contains all of the
following:

- Chrome URL/build inspected and the date/time of inspection.
- Changed user flow(s) tested.
- Desktop, tablet, and mobile viewport checks completed.
- Keyboard/accessibility checks completed.
- Design-principle check completed, with issues fixed or explicitly logged.
- Screenshots or a stated reason artifacts could not be retained.

Any later agent must treat this checklist as mandatory acceptance criteria, not
as a suggestion.

### Per-sprint execution checklist

For every sprint, the implementing agent should follow this sequence:

1. Read the relevant section of this specification and inspect the referenced
   backend model before changing code.
2. Confirm input/output fields and produce or update a minimal fixture that
   exactly matches the JSON contract.
3. Build the smallest end-to-end path for the sprint goal, including loading,
   empty, and error states.
4. Add automated tests for rendering and contract mapping; use visual checks for
   responsive layouts and chart/table readability when applicable.
5. Verify that the browser performs formatting and state management only—not
   financial calculations, FX conversion, tax logic, XIRR, or date resolution.
6. Compare displayed values, dates, warnings, methodology version, and currency
   labels against the fixture/artifact.
7. Update this specification and the implementation backlog if a missing backend
   field, artifact, or methodology ambiguity blocks the next iteration.
8. Finish with a concise sprint review: delivered behaviour, tests run, known
   limitations, and the next unblocked sprint.

### Backlog rules and dependencies

- **Do not bypass a backend gap in the browser.** If a view needs a value not
  provided by a contract, add a backend/artifact task rather than calculating an
  approximation client-side.
- **Treat charts as a backend-data dependency.** `AnalysisResult` contains
  summary output, not a historical value series.
- **Treat comparison as a contract dependency.** Multiple single-security
  result artifacts can be displayed side by side only when inputs, methodology
  versions, and data snapshots are compatible.
- **Keep native currency generic.** The UI must use the security's currency;
  USD is an example, not a hard-coded application mode.
- **Prefer thin vertical slices.** A complete, trustworthy single-security SGD
  result is more valuable than partially implemented charting, portfolio, and
  comparison screens.

## Sprint 9 UI request identity contract — frozen 15 October 2026

This presentation contract does not alter engine requests, worker protocol,
result envelopes, financial calculations, warning semantics, or provenance.
Each view (`analysis`, `dca`, `compare`, `portfolio`) owns independent draft,
generation, phase, completed request, artifact, chart, coverage, and display
currency. Selecting or changing display currency in one view cannot mutate
another view's selection, completed result, chart, warnings, or export.

A submitted request is copied immutably before any await. Identity includes the
view, security ID (ordered security IDs/tickers for comparison), requested dates,
initial capital, recurring contribution and frequency for DCA, optional initial
lump sum (reserved default 0 for Sprint 11), scenario booleans, and full ledger
rows/as-of date for portfolio. Completed identity also retains producer,
methodology version and data snapshot from the actual returned envelope.
Requested and resolved dates are distinct. Never derive export/share identity
from an edited form or from resolved dates in place of requested dates.

States: empty → loading → current; an edit immediately invalidates in-flight
work and moves a completed result to previous (or an empty view to pending).
Validation, unavailable coverage, and load/compute failures enter invalid or
failed while any retained result stays explicitly previous. Submit moves to
loading; a response can commit only if its view generation still matches.
Editing, including an invalid edit during a pending request, advances generation
before validation. Older success/error/progress/finally handlers cannot overwrite
newer state. Display-only currency changes do not change financial identity.

Financial edits never auto-calculate. Calculate/Update explicitly submits.
Automatic series prefetch may not replace a completed result's attached chart.
A completed chart must have the same security and requested window as its
result, or be omitted. Previous output includes its original input summary;
JSON, CSV and share controls explicitly identify that previous request.
Coverage and warnings are attached to the completed request and survive display
currency changes. No latest-coverage date is invented if not published.

## Sprint 11 simulator contract and methodology amendment

One mounted simulator form owns a selected security, requested dates and
assumption switches. One-time capital is retained separately from initial lump
sum and recurring amount/frequency. Explicit mode buttons preserve those values;
shared edits invalidate both applicable results and amount-only edits invalidate
their own mode. Switching away from a loading mode invalidates its outstanding
response. Errors, completed requests, price data and display currency remain
per mode. Session storage retains drafts only; reload starts with empty results,
never old numbers presented as current. The existing ledger store is unchanged.

DCA requests accept optional `initial_sgd` (decimal string), Python accepts
`initial_sgd=0`, and JS accepts `initialSgd='0'`. Initial capital is bought once
at the resolved first purchase date, additional to the first recurring payment.
Recurring contribution dates/count remain unchanged. Total capital, native
capital, shares and dated cash flows include the lump sum. Zero/omitted amounts
preserve the old result shape and methodology; nonzero methodology adds the
initial amount/date and version 1.1. The worker change is additive and optional;
existing request keys include this field through the existing canonical payload.

Price charts show one display currency at a time with numeric/date axes and a
matching data table. They are explicitly price history, not wealth or total
return. A narrow screen can scroll the chart horizontally; the table remains
an alternative. CAGR and XIRR are explained as different return measures.

Comparison handoff is explicit and one-time only. It copies security, capital,
requested dates and exact assumptions; adding/editing comparison inputs cannot
mutate the simulator draft/result. Regular-mode handoff explains the limitation
and stays in the simulator. Separate session drafts preserve this independence
on navigation/reload. Preset dates use published security/FX coverage only.
